# Architecture Decision Records — Milestones 1 & 2 (`csai302_db`)

This document records the core engineering design decisions, rejected alternatives, quantitative rationale, and forward-compatibility consequences for Milestones 1 and 2 of `csai302_db`, following the 4-part ADR template in `docs/docify.md`.

---

## ADR-001: Fixed 8,192-Byte Pages (`struct` + `memoryview`) vs. 4 KB Pages or Python Object Serialization
* **Status:** Accepted (Waves 1–2)
* **Context:** CSAI 302 Milestone 1 prohibits embedded databases (`sqlite3`, `duckdb`, etc.) and Python object serialization (`pickle`, `shelve`, `marshal`), and Milestone 1–2 require a unified physical storage unit capable of hosting row heaps (`*.db`), columnar chunks (`*.col`), and B+ Tree nodes (`*.bpt`) with torn-page integrity checking and Free Space Map (FSM) page reuse.
* **Alternatives Considered:**
  * **Option A: 4,096-Byte Pages with JSON/Pickle Payloads (Legacy Prototype Approach).** Pros: Simple object encoding and small OS page alignment. Cons: Violates anti-cheat rules (`pickle`), incurs massive JSON parse/serialization overhead and space bloat, shrinks B+ Tree fanout by ~2x, and caps single-page FSM coverage at ~32,512 pages (~127 MB).
  * **Option B: Variable-Size Record Blocks Without Fixed Page Geometry.** Pros: Eliminates internal page fragmentation for arbitrary tuple sizes. Cons: Breaks fixed-size buffer pool frame reuse across tables and indexes, prevents $O(1)$ positioned offset calculation (`page_id * PAGE_SIZE`), and complicates FSM bitmaps.
  * **Option C: Universal 8,192-Byte Pages (`PAGE_SIZE = 8192`) with 32-Byte `<IBBHQIIQ` Header, BLAKE2b-64 Checksum, and Page 0 FSM.** Pros: Uniform frame size across all relational and B+ Tree structures, high B+ Tree fanout ($M_{\text{leaf}} \approx 340$ for 8-byte keys + 8-byte `RID`), zero-copy `memoryview` slicing, and $65,280$-page (~510 MB) single-page FSM capacity (`fsm_offset = 32`, or `65,024` pages at `fsm_offset = 64` for B+ Trees). Cons: Single relational tuples/strings are bounded to `8,140` user payload bytes (`SlottedPage`) or `8,156` UTF-8 bytes (`ColumnPage`), and single-FSM files max out at ~510 MB.
* **Decision & Rationale:** Adopted **Option C** across `src/common/config.py`, `src/storage/page_header.py`, and `src/storage/disk_manager.py`. Every page starts with the exact 32-byte little-endian `<IBBHQIIQ` header (`page_id`, `page_type`, `flags`, `slot_count`, `page_lsn`, `free_space_ptr`, `next_page_id`, `checksum`) and stores a 64-bit `BLAKE2b(digest_size=8)` checksum over `buf[0:24] + buf[32:8192]` stamped on every `DiskManager.write_page()` and verified on every non-zero `DiskManager.read_page()`. Doubling page size from 4 KB to 8 KB amortizes the 32-byte header to `0.39%` overhead per page while fitting `1,020` 8-byte scalars per columnar chunk (`(8192 - 32) // 8 = 1020`) and keeping single-bit disk corruption strictly detectable via `PageCorruptedError`.
* **Consequences & M3–M6 Impact:**
  * **M3 (Query Processing):** Uniform 8,192-byte pages let `CatalogManager` and the Cost-Based Optimizer model sequential and random scan I/O directly in 8 KB page units.
  * **M4 (MVCC & ARIES Recovery):** Bytes `8..15` of every page header permanently reserve `page_lsn: uint64` (exposed via `PageHeader.get_page_lsn` / `set_page_lsn`) so ARIES Redo/Undo and WAL flush enforcement attach without migrating M1–M2 disk files.
  * **Limitation:** Single-page FSM capacity caps individual `.db`/`.col`/`.bpt` files at 65,280 / 65,024 pages (~510 MB) until multi-extent FSM chaining is added if needed later.

## ADR-002: Unified 64-Bit `RID(page_id, slot_id)` Across Slotted Row and Columnar Layouts
* **Status:** Accepted (Waves 1–2)
* **Context:** The Retail schema mixes OLTP row tables (`customers`, `products`, `inventory`, `orders`) with an OLAP columnar table (`order_items`) and secondary B+ Tree / LSM indexes across both layouts. Indexes and query operators need a uniform, immutable 8-byte record pointer (`<II`) that stays valid even when row pages defragment or column files store one file per column.
* **Alternatives Considered:**
  * **Option A: Separate Physical Pointer Formats for Row vs. Column Tables (e.g., `(page_id, byte_offset)` for rows and 64-bit row ordinal for columns).** Pros: Direct byte addressability on row pages. Cons: Breaks `SlottedPage.compact()` (compaction shifts tuple byte offsets, invalidating every external index entry) and prevents a single `BaseIndex` / `SimpleExecutor` contract across `RowTableHeap` and `ColumnTableHeap`.
  * **Option B: Shifting Slot Directories on Delete in `SlottedPage`.** Pros: Keeps slot array dense without `(0, 0)` tombstones. Cons: Shifts `slot_id` of subsequent live rows on the page, corrupting external `RID`s held in B+ Tree and LSM Tree indexes.
  * **Option C: Unified 64-Bit `RID(page_id: uint32, slot_id: uint32)` with Non-Shifting Slotted Directories and Lockstep Column Chunks (`CHUNK_ROWS = 1020`).** Pros: `SlottedPage.compact()` updates only `tuple_offset` in each 4-byte `<HH` slot entry and `delete_tuple()` zeroes `(0, 0)` without shifting indices; `ColumnTableHeap` advances all column `.col` files together at `chunk_rows = 1020` (yielding `1,020` 8-byte values per page with zero-copy `np.frombuffer(..., offset=32)`), so `(page_id, slot_id)` indexes the exact same logical row across all 5 `order_items` files. Cons: Tombstoned slots permanently consume 4 bytes per deleted tuple until page vacuuming, and `RowTableHeap.update()` overflows must relocate to a new `RID` (requiring caller/executor index updates).
* **Decision & Rationale:** Adopted **Option C** in `src/common/types.py`, `src/storage/slotted_page.py`, `src/storage/column_page.py`, and `src/storage/table_heap.py`. Every `SlottedPage` tuple includes the 16-byte `<QQ` MVCC header (`xmin = 1, xmax = 0`) followed by `Schema.encode_row()` bytes, while `ColumnPage` packs C-contiguous fixed-width scalars starting at byte 32 (yielding `arr.flags["OWNDATA"] is False` zero-copy NumPy views) and supports arbitrary fixed-byte `stride` values (`stride = 1536` fits `5` 384-d `float32` vectors per page).
* **Consequences & M3–M6 Impact:**
  * **M3 (Vectorized Execution):** `ColumnTableHeap.iter_batches()` yields aligned `{col: np.ndarray}` chunks of up to `1,020` zero-copy rows per page while pinned in `try/finally`.
  * **M4 (MVCC):** `SlottedPage.get_tuple_mvcc_header()` and `set_tuple_xmax()` operate in place on the 16-byte `<QQ` prefix without changing tuple offsets or `RID`s.
  * **M5 (Distributed Sharding & Vector Search):** Immutable `RID`s and `ColumnPage(..., stride=1536)` directly enable `products.desc_vec.col` 384-d cosine similarity and shard-local index routing without changing M1 binary page layouts.

## ADR-003: $O(1)$ `OrderedDict` Pin-Aware `BufferPoolManager` with Pluggable `LRU` and `FIFO` Policies
* **Status:** Accepted (Waves 1–2)
* **Context:** Every table heap and B+ Tree index shares a bounded memory frame budget and must support pluggable eviction policies (`LRUReplacer` and `FIFOReplacer`), concurrent thread safety under a strict lock hierarchy, strict pin-count protection (`BufferPoolFullError` when all frames are pinned), dirty write-back before eviction, and accurate hit/miss/eviction telemetry.
* **Alternatives Considered:**
  * **Option A: Linear Scan Over Frame Array or Doubly-Linked List in Pure Python.** Pros: Simple array scan for small pools. Cons: $O(\text{pool\_size})$ victim selection degrades on larger buffer pools, while custom pointer nodes in Python add object allocation and GC overhead.
  * **Option B: `functools.lru_cache` or `FIFOReplacer` Deleting/Re-inserting on Hit.** Pros: Minimal code. Cons: `lru_cache` lacks explicit `pin_count` guards, dirty-page flush hooks, and `new_page()` frame reservation; naive `OrderedDict` `pin()`/`unpin()` on `FIFOReplacer` corrupts arrival order when a cached page is temporarily pinned on a hit and unpinned afterward.
  * **Option C: `collections.OrderedDict`-Backed `LRUReplacer` and Arrival-Preserving `FIFOReplacer` Inside `BufferPoolManager`.** Pros: $O(1)$ amortized `pin`, `unpin`, `victim`, and `remove`; `FIFOReplacer` tracks `_od` (arrival order) plus a `_pinned` set (`_pinned <= _od.keys()`) so cache hits temporarily shield a frame from eviction without moving it to the FIFO tail; `new_page()` secures/flushes a victim frame *before* calling `DiskManager.allocate_page()` so `BufferPoolFullError` never leaks orphan FSM pages; `threading.RLock` enforces `BufferPoolLock -> DiskManagerLock`. Cons: `FIFOReplacer.victim()` is $O(P + 1)$ in the worst case when the oldest $P$ frames in `_od` are currently pinned (still $O(1)$ when the head is unpinned and negligible relative to disk I/O).
* **Decision & Rationale:** Adopted **Option C** in `src/storage/replacer.py` and `src/storage/buffer_pool.py`. `FrameHeader` keeps each frame's `bytearray(8192)` fixed in place and resets via slice assignment (`self.data[:] = _ZERO_PAGE`) so live `memoryview` handles never lose alignment. `ReplacementPolicy.remove(frame_id)` cleanly separates permanent page deletion (`delete_page()`) from temporary `pin()`/`unpin()` cycles.
* **Consequences & M3–M6 Impact:**
  * **M2–M3 (B+ Tree & Joins):** Pin protection guarantees safe 2-frame latch-crabbing in `BPlusTreeIndex` (tested on a 3-frame pool) and keeps `ColumnPage` zero-copy NumPy buffers pinned during `iter_batches()` execution.
  * **M4 (ARIES WAL):** `_flush_frame_if_dirty()` already isolates the single write-back hook (`# M4 ARIES WAL hook: enforce flushed_lsn >= PageHeader.get_page_lsn(frame.data)`) required to enforce Write-Ahead Logging before dirty eviction.

## ADR-004: Extent-Based Encrypted `ObjectStore` (`AES-256-GCM` with `oid` AAD Binding) vs. OS-File-Per-Image
* **Status:** Accepted (Waves 1–2)
* **Context:** Retail products reference variable-sized binary image payloads (`10 KB` to `250 KB`) via `products.image_oid` (`UINT64`). Storing large blobs inside 8 KB relational pages exceeds single-page capacity, while `00_AGENT_GOVERNANCE.md` forbids storing one OS file per object. Additionally, Milestone 2 requires pluggable `AES-256-GCM` authenticated encryption that prevents both ciphertext inspection and cross-object ciphertext swapping.
* **Alternatives Considered:**
  * **Option A: OS-File-Per-Object (`objects/<oid>.bin`).** Pros: Trivial OS read/write/delete. Cons: Explicitly forbidden by governance rules, exhausts filesystem inodes/dentries, and causes severe directory-lookup and open/close syscall overhead.
  * **Option B: Overflow Page Chains Inside 8 KB `DiskManager` Pages or Unauthenticated Encryption.** Pros: Reuses buffer pool pages. Cons: Adds multi-page pointer-chasing fragmentation for 250 KB objects and exposes objects to silent tampering or cross-OID ciphertext substitution if `oid` is not bound into AEAD AAD.
  * **Option C: Dual-File Extent Store (`objects.dat` + `objects.dir`) with Pluggable `CipherHook` (`NoOpCipher` / `AES256GCMHook`) and Per-OID AAD Binding.** Pros: Appends sequential variable-length extents in `objects.dat` with a 48-byte `<4sQII12s16s` header (`magic=b"OBJ1"`, `oid`, `raw_len`, `cipher_len`, 12B `nonce`, 16B `tag`) + `ciphertext` + 4-byte `<I` CRC32 trailer; maintains $O(1)$ in-memory `oid -> ObjectMeta` lookup backed by atomic `.tmp -> fsync -> os.replace` writes to `objects.dir` (`<4sI` + 24-byte `<QQII` entries); binds `aad = struct.pack("<Q", oid)` into `AESGCM` so even CRC32-recomputed cross-OID swaps fail with `SecurityViolationError`. Cons: Deleted extents leave unreferenced space in `objects.dat` until offline compaction, and `objects.dir` must fit in memory as a dictionary.
* **Decision & Rationale:** Adopted **Option C** in `src/storage/cipher_hooks.py`, `src/storage/object_store.py`, and wired into `StorageEngine.object_store` (`src/storage/storage_engine.py`). Sequential extent appends eliminate per-file inode syscalls and 8 KB page-splitting overhead, while dual CRC32 + `AES-256-GCM` with `aad = pack("<Q", oid)` provides strict integrity and confidentiality guarantees. `StorageEngine` also persists standalone `storage_meta.json` atomically so both relational heaps and the encrypted `ObjectStore` survive restarts independently of `CatalogManager`.
* **Consequences & M3–M6 Impact:**
  * **M2–M6 (Encryption & Media Serving):** `NoOpCipher` (`algorithm_id = 0`) and `AES256GCMHook` (`algorithm_id = 1`) share an identical envelope layout, enabling controlled encryption-overhead benchmarking (Exp 2D) and drop-in key rotation or KMS hooks in later milestones without changing on-disk framing.
  * **Known Bound:** `ObjectStore.delete_object()` removes the directory mapping in `objects.dir` without compacting dead extents in `objects.dat`; offline extent compaction can be added later without changing the `OBJ1`/`ODIR` binary format.
